# 正确性地基：存档、日输入、状态机、不变量

日期：2026-11-27。依据：下游 hrhgit/Keynes 的 [PR 15](https://github.com/hrhgit/Keynes/pull/15)（合并上游）、[PR 16](https://github.com/hrhgit/Keynes/pull/16)（静态护栏）、[PR 17](https://github.com/hrhgit/Keynes/pull/17)（同日重访后续修复）的历次独立复审，共约 40 条 High/Medium 发现。本页排一组共用机制的设计、顺序和验收，目标是让这几类错误由结构排除，而不是靠每个模块的实现者和审查者逐个找出来。目标架构见 [design.md](../architecture/design.md)。

## 为什么要做

### 复审发现的分布

| 类别 | 典型发现 | 出现在 |
|---|---|---|
| 存档 | 拒绝坏档前已改动原世界；合法存档被拒；旧版程序静默丢掉新档数据；读档后再存丢值；字段越界不校验；加了字段不升版本；冷读档后逐日结果不同 | #15、#16、#17，每轮都有 |
| 输入时序 | Effect 登记的生效日、事务号取决于到达顺序；回执的处理时刻取决于线程是否跑完；错误回执吞掉正确回执；改成按日边界取回执后，RETRY 不再重送导致当天卡死 | #17 连续四轮 |
| 跨日协议状态 | 建筑停业、复工、试营业、清算之间的计数互相干扰；换代后旧事务号被迟到回执清掉，实例永久跳过 | #15 六轮、#17 |
| 同日重访 | 已完成的阶段没有沿用结果，同一修正叠加两次 | #11 |
| 静态检查语义 | 用文本规则判断 C++ 语义，每轮都有新的漏报和误报 | #16 三轮 |

### 根因

这些都不是某个模型能力不够造成的。[design.md](../architecture/design.md) 已经把对应的机制列为"目标，尚未实现"：统一的候选安装与世界级回滚、全域统一去重、消除剩余软完成。机制不存在，每个模块就各写一份：

- **存档。** 每段各自手写字节读写（`d7_read_u32` 一类），各自决定版本和缺省值。世界级恢复按段依次调用各权威的 `restore()`，前面的段已经装进活对象，后面的段失败时没有回滚（`native_simulation_host_startup_section_restore_authorities.inc`）。经济段在 #15 第七轮改成"暂存后整体安装"，第八轮马上暴露出暂存时重新配置、备份时又做校验的问题。这些都是在一个模块里临时补出的局部版本。
- **输入。** 玩家命令已有按日封口（`RuntimeCommandAdmission`），Effect 登记、指标和回执是后来各自加的队列，各有各的锁和取用时机。回执还有两条通道：执行器内的同步适配器（`stage_effect_adapter`），和前台 `effect_facade.gd` 轮询后再提交的异步通道。异步通道的处理时刻天然取决于线程快慢。
- **跨日协议。** 事务、建筑生命周期的状态散落在多个计数和标志里，转移规则分布在多个函数中，没有一处能列出"所有状态 × 所有事件"。审查者只能顺着代码路径找反例，修一处，相邻的组合又冒出来。

要保证的性质是全局的（"任何失败都不改世界""结果与到达时刻无关"），实现却是 N 份局部代码。审查每轮都能在第 N+1 份里找到漏洞，换更强的模型只是找得更快。

## 设计

四个机制，各自对应上表一类问题。每个机制都是一个共用实现和一套自动生成的测试：模块接入机制，就自动获得这些性质和测试，不再由模块自己证明。

### A. 存档：段描述 + 恢复事务

**段描述。** 每个存档段用一份数据描述：字段名、类型、取值范围、引入版本、旧版缺省值或迁移函数。编解码由描述驱动，不再手写字节偏移。

- 版本号与描述的指纹一起登记在基线里。字段集变了、版本没升，比对描述指纹就能查出来。描述是数据，不用解析代码，这条检查可以做到零误报。#16 里 `narrative_save_layout.py` 那类文本启发式随之退役。
- 越界、缺字段、多余字段由描述统一拒绝，不再逐段手写校验。
- 新版写出的段带"最低可读版本"。旧程序读到更新的段时明确拒绝，不会静默丢弃（#17 的 PKSR v6 问题）。

**恢复事务。** 世界级恢复固定分三步：

1. **解码**：把所有段解码成候选状态。这一步是纯函数，输入只有存档字节和一份冻结的配置快照（目录、修正项定义等），不读任何活状态，也不重新跑配置校验（#15 第八轮的两个问题）。
2. **校验**：候选内部和跨段的一致性检查，例如引用的人群存在、席位与人口吻合、事务指向的实例存在。
3. **提交**：所有权威的候选一次换入，旧状态整体换出后丢弃。前两步任何失败，活世界一个字节都不变。

宿主只保留这一个恢复入口。经济段的流式读档（begin/feed/end）改成只负责把字节喂进第 1 步。

**自动生成的性质测试。** 每个登记的段自动得到下面这些测试，不再由各模块手写：

| 测试 | 内容 |
|---|---|
| 往返 | 用非默认值填满每个字段，容器至少两条且顺序可区分；存、读、再存，两份字节相同 |
| 逐字段拒绝 | 每个字段分别改成越界、缺失、类型错；必须拒绝，且世界状态哈希不变，之后能继续推进并读入合法档 |
| 历史版本 | 每个曾发布的版本保留一份真实写出的夹具，必须能读入并续跑 |
| 读后立即再存 | 已运行过的宿主读档后马上再存，字节与原档相同（#17 的 `climate_anomaly` 问题） |
| 冷读一致 | 任一天存档、冷读、续跑 N 天，逐日结果与不存档直接跑相同 |

### B. 日输入：统一的按日封口收件箱

**一个入口。** 所有进入模拟的输入走同一个收件箱：玩家命令、环境输入、Effect 登记、指标、移除、回执、测试注入。每条输入带"来源、来源内序号"。

**按日封口。** 收件箱按模拟日分格。日边界封口后，第 D 天只读封给 D 的那一格，并在格内按（来源，序号）排序。到达时刻只决定一条输入落进哪个还没封口的格子，而且这由封口规则决定，与线程处理到哪无关。这是把命令已有的 `RuntimeCommandAdmission` 推广到所有输入。

**同日跨域交接不走邮箱。** Effect 发给 Country、Economy 的请求，由执行器在 Resolve 阶段按固定顺序同步交给所有者，所有者当场给出结果。RETRY 只表示"所有者决定下一天再试"。它是写进事务状态的业务结果，下一天开日时确定性地重送，不能表示"还没处理到"。

**前台通道。** 前台轮询请求、提交回执的通道只保留给非整图授权的测试，它提交的回执同样进收件箱。整图授权下，正式路径只有执行器内的同步交接。

这一项同时完成 [架构解耦计划](architecture-decoupling-plan.md) P2 的一部分："停在日界"的请求也是一种输入。

### C. 跨日协议：表驱动状态机

凡是跨日保持状态的协议，都写成一张转移表：状态 × 事件 → 新状态 + 动作。包括 Effect 事务、实例换代、建筑生命周期、命令等待和玩家待答。

- 转移只在一处执行（一个函数里一张表或一个 switch），状态是一个枚举值加少量参数，不再由多个计数和标志拼出来。
- 表本身生成组合测试：每个状态 × 每个事件 × 是否在这一刻存读档。每个组合检查四条不变量：结果只由日边界决定；每个非终态都有能推进它的事件，不会卡死；状态引用的对象都存在；存读档前后状态字节相同。
- 新增状态或事件时必须补全表里对应的行和列，缺一格编译或测试就失败。
- 表写进 `feature-guides.md` 对应一节，代码和文档引用同一张表。

建筑生命周期在 #15 已经按"先写状态表"重做过一次，是这个机制的第一个实例。下一步按同样格式把它收进统一的表驱动实现。

### D. 每日不变量探针

每天提交后，对已提交状态跑一组不变量检查，CI 和调试构建默认开启。目前已有 `economy_invariant_probe`，推广到各域：

- 守恒：钱、货、人在跨域交接前后总量一致；
- 引用：席位、事务、实例、等待项指向的对象都存在；
- 活性：每个等待项都存在能推进它的输入或日期；
- 发布：发布帧与已提交状态的摘要一致。

探针失败即停，报告第一处违反和当天的输入摘要。它负责抓 A、B、C 没覆盖到的组合，把"审查者读代码想反例"变成"跑一遍就知道"。

## 不在范围

- 游戏规则设计本身（工资口径、选材、清算策略），按上游的规则来，只记录问题。
- 性能：这四个机制都不进热循环。A、B 只在存读档和日边界运行。C 的表驱动只替换现有的分支，不增加工作量。D 只在 CI 和调试构建默认开启。

## 顺序和验收

每一步单独一个 PR，各自跑完整回归、回放矩阵和逐日确定性检查（空闲、加压各 10 遍）。

| 步骤 | 内容 | 验收 |
|---|---|---|
| 1. A 框架 | 段描述、描述驱动的编解码、三步恢复事务、自动性质测试；先接入叙事存档和 Effect 传输两段 | 两段通过全部五类性质测试；宿主恢复只剩一个入口；与改前逐日结果零差异 |
| 2. A 推广 | 其余段逐段接入，每个 PR 一到三段，经济段放最后 | 每段通过五类测试；手写字节读写清零；`narrative_save_layout.py` 改为比对描述指纹 |
| 3. B | 统一收件箱；Effect 登记、指标、回执并入；同日交接由执行器同步完成；RETRY 改为次日重送 | 输入到达时刻随机打乱 100 次，逐日结果全部相同；正式路径上没有异步回执 |
| 4. C | Effect 事务与建筑生命周期改为表驱动，生成组合测试 | 组合测试全过；表与 `feature-guides.md` 一致 |
| 5. D | 不变量探针推广到各域 | 365 天固定场景和回放矩阵下探针零违反 |

步骤 1 排在架构解耦计划的 P1 之前：P1 删镜像时会改恢复路径，先有恢复事务可以省掉一轮返工。步骤 3 与 P2 合并。

## 落地方式：做进上游

这四个机制是所有模块共用的地基，只留在下游分支里，上下游会越分越远：上游新加的模块继续按旧办法各写一份，每次合并上游都要重新接入，同类错误还会再出现。所以地基要送进上游（HkingAuditore/Project.Keynes）。

- **以上游 master 为基座。** 每一步以当时的上游 master 为基础，顺序见[架构路线图](architecture-roadmap.md)。
- **每一步整理成一个上游 PR。** 说明里写清动机、对现有行为的影响（应为零差异）和验证结果。
- **PR 只依赖仓库里的东西。** 写进仓库的规则、脚本和测试不依赖任何特定的 AI 工具或本机环境，上游协作者用自己的工具就能运行和审查。
- **先接入上游正在改的模块。** 上游近期改动最频繁的是建筑经营。步骤 2 和步骤 4 优先接入它，让上游后续的改动直接走新机制，不再积累手写的读写和状态。
- **上游暂时没有合并时，** 下游照常推进，但每一步都保持能原样提给上游：不夹带只属于下游的改动，避免分叉。

## 对在途 PR 的处理

#15、#16、#17 已停止修补，各自可复用的部分由哪一步吸收，见[架构路线图](architecture-roadmap.md#在途-pr-的去向)。

## 流程上的配套

- 新增跨日协议或存档段，先在 `feature-guides.md` 写状态表或段描述，再写代码；审查先对表，再对代码。
- 复审提示词按性质限定范围，例如"任一失败不改世界""结果与到达时刻无关"，并附上对应的自动测试。审查者找到反例时，先补进自动测试，再修代码。
- 同一处连续两轮审查都有新的 High/Medium，就停止逐条修补，回到"缺了哪个共用机制"。
