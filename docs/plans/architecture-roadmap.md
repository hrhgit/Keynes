# 架构路线图

本文把[正确性地基](correctness-foundations.md)、[架构解耦计划](architecture-decoupling-plan.md)（P0–P5）、[执行队列](execution-queue.md)第 13 项和 [design.md](../architecture/design.md) 中“目标，尚未实现”的条目合成一个顺序，分为“先做”和“后补”两段。各项的设计细节仍以原文档为准，本文只规定顺序、基座和在途改动的去向。

## 现状（2026-11-27）

- 上游 HkingAuditore/Project.Keynes 的 master 为 `39040c5ce`。它与本仓库 master `919223665` 的直接差异为 952 个文件。上游在 11-28 又合入两个大提交，共 212 个文件，主要改了建筑经营、开局经济、税务界面、世界生成和渲染。
- 本仓库的 #6（拆分超长文件）和 #8（性能优化）已由上游分别作为其 PR #3 和 #4 合入。上游还没有的是 #9（P0–P3）、#10（删无用镜像）、#11（Modifier 同日重复应用）、#12（Modifier 只读视图）、性能与检查工具，以及规则和计划文档。
- 在途的 PR 已停止修补，分支和 PR 保持原样：
  - #15（合并上游）：九轮复审没有收敛；上游此后又前进两个提交，这条分支已经过时。
  - #17（Effect 定序与回执封口）：仍有 1 个 High、1 个 Medium 未修。
  - #16（静态护栏改运行时测试）：最新修复在本地提交 `3e74f3921`，尚未推送。
- 根因见正确性地基的“为什么要做”一节：存档恢复、输入接收和跨日状态都由各模块各写一份，审查每轮都会在新的一处找到同类问题。

## 基座：上游 master

地基每一步以当时的上游 master 为基础，在本仓库的分支上完成，再原样提给上游。本仓库 master 不再作为开发基座，现有内容保留不动。

选上游的理由：地基改的是存档恢复和日输入的入口，这两处恰好是上下游差得最多的地方。上游比本仓库 master 多 66 个提交；本仓库独有的代码只有 #10、#11、#12，约 160 个文件。以本仓库为基座，就要重做一次 #15 那样的大合并，以后每次同步上游还要再接一遍。

本仓库独有的改动按下表的步骤，在上游代码上先写出会失败的测试，再重做，不整体搬运。

## 先做

按顺序执行。每一步单独一个 PR，验收沿用正确性地基“顺序和验收”一节：完整回归、回放矩阵、逐日确定性检查（空闲、加压各 10 遍），与改前逐日结果零差异（修 bug 的步骤除外，差异要逐项解释）。

| 步 | 内容 | 吸收的在途改动 | 来源 |
|---|---|---|---|
| 0 | 在上游 master 上建立基线：跑通静态护栏、完整回归、回放矩阵和确定性检查，把上游现有的失败逐条登记，不修 | — | — |
| 1 | 错误修复：上游现存的确定性、存档、卡死和崩溃问题，每条先在上游代码上复现。已知候选：Modifier 同日重复应用、税表行键碰撞（固定税 1 与 16777217 落在同一行）、Effect 登记顺序依赖到达时刻 | #11；#17 的修复 D 和定序修复；#16 的运行时测试（税表、叙事存档） | 地基“落地方式” |
| 2 | 存档段描述与恢复事务（地基 A 的框架）：先接入叙事存档和 Effect 传输两段，宿主恢复只剩一个入口 | #17 的 ETQ2 校验；#16 的叙事往返测试和坏档拒绝测试并入自动性质测试 | 地基步骤 1；design.md“统一的候选安装与世界级回滚” |
| 3 | 存档段逐段接入，建筑经营和经济段放最后 | #15 的“暂存后整体安装”和 PKEC 历史版本夹具 | 地基步骤 2；design.md“统一 provider 注册” |
| 4 | 统一日输入：一个按日封口的收件箱，同日跨域交接由执行器同步完成，RETRY 表示次日重送；释放上限收拢到一处 | #17 的回执封口；执行队列第 13 项第 0 步遗留的 Economy POD 命令封口，以及第 2 步一天中途向主线程采集经济输入的问题 | 地基步骤 3；解耦 P2；design.md“全域统一去重” |
| 5 | 表驱动状态机：Effect 事务、建筑生命周期 | #17 的事务状态表与组合测试；#15 中与确定性和存档有关的建筑结算修复，改写为状态表的行。玩法规则问题只记录给上游 | 地基步骤 4 |

第 1 步排在地基之前，是因为这些问题会让第 0 步的基线和后面每一步的确定性检查失败。第 2 到 5 步的先后顺序沿用正确性地基：恢复事务先于删除镜像，统一日输入与 P2 合并。

## 后补

以下各项依赖“先做”的成果，或者需要先与上游商量边界。顺序暂不固定，先做完时再排。

| 内容 | 为什么放后面 | 来源 |
|---|---|---|
| 不变量探针推广到各域 | 需要第 4、5 步给出的统一输入和状态表，才有稳定的检查点 | 地基步骤 5 |
| 单一时间线收尾：删除主线程镜像（Modifier → Effect → Trigger → Ideology → Country），前台直读归零，测试改为同步推进 | 删镜像会改恢复路径和输入路径，先有第 2、4 步可以省掉一轮返工；同时改动上游的界面代码，要先与上游商量 | 解耦 P1；执行队列第 13 项第 1、4、5 步；#10、#12 在上游代码上重做 |
| 删除 SHADOW 与对拍代码 | design.md 规定在黄金回放覆盖充分之前保留 | 解耦 P1 待定项 |
| 黄金回放覆盖全部 12 个域的哈希 | 每步验收已经跑确定性检查；全域哈希是 SHADOW 删除的前提，与上一项一起做 | design.md 黄金回放 |
| Family 改为 Economy 子模块 | 上游正在频繁修改经济，现在重做冲突最大；等第 3、5 步把经济段和建筑生命周期接入新机制之后再做 | 解耦 P3；#9 |
| Economy 内部分区（多写成员 96 个降到 20 个以下） | 依赖第 5 步的状态表划定写入方 | 解耦 P4 |
| Ideology、Effect、Trigger、Climate 的 API 头文件；19 个域对逐函数核查；描述符内核强制 | 模块边界的整理，不影响正确性，排在机制落地之后 | 解耦 P5；design.md 模块 API |
| 静态护栏改为“拦截原样复发”加运行时测试 | 运行时测试已在第 1、2 步并入；剩下的静态部分作为“契约与护栏”PR 提给上游 | #16 |

## 不属于本路线

- 执行队列中的第 8 项（绑定拆分阶段 3）、第 12 项（智能体开发框架）、第 15 项（运行时故障基建）、第 16 项（降水频率）和 Web 回退第 2 步仍按原排期，与本路线无先后依赖。
- 本仓库去掉 Qodo 的工作（`AGENTS.md`、`docs/factory/`、`tools/factory/`）只涉及下游，随时可做，不占本路线的顺序。
- 上游玩法规则层面的问题（工资口径、选材、空置与清算策略等）只记录在对应上游 PR 的“已知但未改的上游问题”一节，不改代码。
